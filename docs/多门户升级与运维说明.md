# 多门户升级与运维说明（部署 / 维护人员）

日常门户管理在网页完成（见 `docs/门户管理使用说明.md`）。本文只覆盖：新装、旧库升级、应急命令、备份回滚、部署检查。

## 1. 环境变量

| 变量 | 说明 |
|---|---|
| `DATABASE_URL` | MySQL / MariaDB 连接串 |
| `REPAIRNOTE_ADMIN_USERNAME` / `REPAIRNOTE_ADMIN_PASSWORD` | **仅空库首次安装**使用：创建首位账号，同时是系统主管理员和默认门户管理员。密码必须是真实密码：为空、`admin123`、`123456`、`change-this-before-deploy` 等默认 / 占位 / 弱密码会让初始化直接失败、不创建任何账号（生产至少 8 位）。已有账号时不再使用，也不会重置密码。 |
| `REPAIRNOTE_PUBLIC_ORIGIN` | 浏览器访问本系统的唯一 origin（例如 `https://repair.example.com`，不带路径）。系统管理写接口只接受来自该 origin 的请求；缺失或不合法时 `server.js` 拒绝启动，管理写接口全部 403。启用 `REPAIRNOTE_COOKIE_SECURE=true` 时必须是 https。 |
| `REPAIRNOTE_SYSTEM_ADMIN_STAFF_ID` | **仅旧单门户库升级**时必填：原管理员的 `Staff.id`，升级后成为唯一的初始系统主管理员。不按名字猜测，不提升全部旧管理员；缺失、不存在或原本不是管理员时预检直接停止。 |
| `REPAIRNOTE_COOKIE_SECURE` | https 部署设 `true` |
| `REPAIRNOTE_SEED_DEMO` | 仅本地开发（非 production）显式设为 `true` 时写入演示数据 |

示例文件：`.env.example`（本地）、`.env.plesk.example`（Plesk）、`.env.vps.example`（Docker/VPS）。

## 2. 统一初始化 / 升级命令

```bash
node scripts/db-setup.mjs
```

它按顺序执行，任一步失败就停止（非零退出）：

1. `scripts/db-preflight.mjs` 预检
   - 空库：通过。
   - 有旧表但没有迁移记录：逐表比较列、索引、外键是否与初始迁移完全一致，一致才标记 `20260703000000_init` 已执行；不一致列出差异并停止（不再只凭 Staff 表存在就盲标）。
   - 旧单门户库：要求 `REPAIRNOTE_SYSTEM_ADMIN_STAFF_ID` 有效且原本是管理员；检查悬空的保修来源引用、缺失客户、多余 Setting 行。
2. `prisma migrate deploy`：执行 `20260917000000_multi_portal`（建 Portal / PortalMember、加 `Staff.isSystemAdmin`、所有业务表回填 `portalId=default`、Setting 改为按门户、复合唯一键与外键、删除 `Staff.isAdmin/pagePermissions`、清空 StaffSession）。
3. `prisma db seed`：空库创建首位系统主管理员 + 默认门户；已有账号时只保证默认门户设置存在。
4. `portal-admin.mjs bootstrap-system-admin --from-env`：旧库升级时把指定账号设为系统主管理员（幂等；已有其他系统主管理员时拒绝）。
5. `portal-admin.mjs check-system-admin`：至少一位系统主管理员、每个门户至少一位门户管理员、每个门户有设置行。

Plesk：`node scripts/plesk-setup.mjs`（内部调用 db-setup 后 `next build`）。Docker：`Dockerfile` 的启动命令是 `node scripts/db-setup.mjs && node server.js`。

## 3. 旧库升级操作顺序（生产）

1. 进入维护模式：停止所有旧版本实例、后台写入和导入脚本，确认没有旧代码继续写库。**绝对禁止旧单门户代码连接升级后的多门户库。**
2. 做数据库完整备份（`mysqldump --single-transaction`），并在独立环境实际恢复验证一次。
3. 在旧库查出原管理员：`SELECT id, username, isAdmin FROM Staff;`，由项目所有者确认，把 id 写入 `REPAIRNOTE_SYSTEM_ADMIN_STAFF_ID`。
4. 记录迁移前快照：`node scripts/verify-portal-migration.mjs --before`（写入 `reports/migration-before.json`：各表行数、金额合计、id / ticket / token / 照片摘要、账号权限）。
5. 执行 `node scripts/db-setup.mjs`。
6. 核验：`node scripts/verify-portal-migration.mjs --after`（行数、金额、token、全部归属 default、成员权限回填、系统主管理员、唯一键 / 外键、旧列已删、旧会话已清空、无悬空引用）。任一失败保持维护，不开放访问。
7. 部署新代码，先用系统主管理员登录验证：设置 → 门户管理 可用；再由该账号在预发布环境走一遍“新建门户 → 分配账号 → 停用 / 启用”。
8. 所有用户需要重新登录一次（迁移清空了旧会话）。

MySQL 的 DDL 会隐式提交，整套 ALTER 不能像业务事务那样自动回滚：**升级中途失败时保持维护模式，用第 2 步的备份恢复数据库并部署匹配的旧代码**，修正后重来。已有新门户写入后不能再直接恢复旧库，必须前向修复。

## 4. 空库新装

1. 在 `.env` 设置 `DATABASE_URL`、真实的 `REPAIRNOTE_ADMIN_USERNAME/PASSWORD`、`REPAIRNOTE_PUBLIC_ORIGIN`。
2. `node scripts/db-setup.mjs`（或 `plesk-setup.mjs` / Docker 启动）。
3. 用首位账号登录，进入 设置 → 门户管理 创建其他门户。

## 5. 应急命令（仅可信宿主机操作者，先做数据库备份）

```bash
node scripts/portal-admin.mjs bootstrap-system-admin --staff-id <现有 default 管理员ID>   # 尚无系统主管理员时指定；已有且指定同一账号则幂等
node scripts/portal-admin.mjs check-system-admin                                       # 健康检查，失败非零退出
node scripts/portal-admin.mjs reset-password --staff-id <账号ID>                        # 隐藏输入新密码，同事务撤销该账号全部会话
node scripts/portal-admin.mjs update-identity --staff-id <账号ID> --name <姓名> --username <用户名> --email <邮箱>
```

- 不接受命令行明文密码，不打印密码 / 哈希，不接受 `isSystemAdmin`。
- 网页上没有授予 / 撤销系统主管理员、删除门户、删除全局账号的功能。
- 属于多个门户的账号和系统主管理账号的密码 / 用户名只能用 `reset-password` / `update-identity` 处理，门店员工页会拒绝。

## 6. 备份与灾备

- 网页备份（备份页）只包含当前门户的业务数据，不含账号、成员、会话；恢复不改身份和门户元数据。每门户最多保留 60 份，自动备份每门户每天一份（业务日按 `Europe/Madrid`，含夏令时切换日）。
- 账号、门户、成员关系的灾备必须用数据库级备份：

```bash
mysqldump --single-transaction --routines --triggers -u<user> -p <db> > repairnote-full-$(date +%F).sql
mysql -u<user> -p <db> < repairnote-full-YYYY-MM-DD.sql   # 恢复（先停写）
```

恢复数据库级备份后必须部署与备份同版本的代码。

## 7. 部署检查（R04）

| 项目 | 要求 |
|---|---|
| HTTPS | 生产必须 https；`REPAIRNOTE_COOKIE_SECURE=true` |
| `REPAIRNOTE_PUBLIC_ORIGIN` | 等于用户在地址栏看到的 origin；反向代理改域名时以对外域名为准 |
| 反向代理头 | 登录限流按 `X-Forwarded-For` 第一个值计数，只有当代理覆盖（而不是透传）客户端发来的该头时才可信；Nginx 用 `proxy_set_header X-Forwarded-For $remote_addr;` |
| 多进程限流 | 应用内限流表按进程独立、有 5000 个键的上限并淘汰过期项；多实例 / 多进程部署时在入口（Nginx `limit_req` 或 Plesk 的对应设置）对 `/api/auth/login` 另加限流 |
| 上传上限 | 备份文件 200MB、外部历史 80MB（应用内）；反向代理 `client_max_body_size` 不得小于该值，且 ZIP 解压后 JSON 同样限制 200MB |
| 数据库 | MySQL 8 / MariaDB 10.6+，InnoDB，默认 REPEATABLE READ；门户写锁使用 `SELECT ... FOR UPDATE` |

## 8. 验证脚本

```bash
npm run build
npm run lint                     # tsc 语法检查 + API 路由鉴权入口检查（不是 next build）
npm run verify:portal-migration -- --before / --after
REPAIRNOTE_TEST_DATABASE_URL=mysql://.../xxx_test REPAIRNOTE_TEST_BASE_URL=http://localhost:3010 REPAIRNOTE_ALLOW_DESTRUCTIVE_TESTS=true npm run verify:portals
REPAIRNOTE_TEST_DATABASE_URL=... REPAIRNOTE_TEST_BASE_URL=... REPAIRNOTE_ALLOW_DESTRUCTIVE_TESTS=true npm run smoke:portals
SMOKE_USERNAME=... SMOKE_PASSWORD=... npm run smoke / smoke:mobile / smoke:mobile:boss   # 本地默认用已安装的 Chrome；无 Chrome 时 SMOKE_BROWSER_CHANNEL=bundled 用 Playwright 自带 Chromium
SMOKE_USERNAME=... SMOKE_PASSWORD=... node scripts/verify-reports-parity.mjs
```

测试脚本只接受以 `_test` 结尾的数据库，并要求 `REPAIRNOTE_ALLOW_DESTRUCTIVE_TESTS=true`；不会回退到生产 `DATABASE_URL`。

## 9. 持续集成（GitHub Actions）

`.github/workflows/ci.yml` 在每次推送和面向 main 的 PR 上自动运行三组任务：

| 任务 | 内容 |
|---|---|
| 构建与静态检查 | `prisma validate` / `generate`、`npm run lint`、`npm run build` |
| 多门户验收（MySQL 8.4） | 空库 `db-setup` 新装 → 启动生产服务 → `verify-portals`（API + 数据库断言）→ `smoke-portals`（浏览器全路径）→ 演示数据上的原冒烟三套与报表对账；报告与截图作为 artifact 上传 |
| 旧库升级演练（MySQL 8.4 / MariaDB 10.11 各一次） | 用初始迁移 + `scripts/fixtures/legacy-single-portal.sql` 构造旧单门户库 → 预检必须拒绝未指定 / 非管理员 / 不存在的系统主管理员与结构篡改 → `--before` 快照 → `db-setup` → `--after` 核验 → 重复执行幂等 |

任一任务失败，PR 页面会显示红叉；合并前请确认三组全绿。
